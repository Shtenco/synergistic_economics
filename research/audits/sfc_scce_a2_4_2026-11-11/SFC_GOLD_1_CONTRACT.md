# SFC-GOLD-1 — frozen financial-event corpus and independent oracle

## Status

**Source implementation committed; exact-head CI execution pending.** This is a
small synthetic control corpus, not empirical evidence, an accounting-standard
certification, or production-runtime integration.

## Purpose

SFC-GOLD-1 establishes a versioned, immutable reference case against which
financial-event semantics and downstream arithmetic can be independently
checked. The corpus is data-only JSON. The oracle is a separate executable
implementation and imports no production journal, SQLite event store,
adapter, SFC projection, or other audit fixture.

The first version deliberately freezes a narrow lifecycle rather than
pretending to cover every financial instrument:

1. bank loan origination creates a loan asset/liability and a matching deposit
   asset/liability;
2. supplier payment transfers an existing deposit from household to supplier
   without creating additional system deposits;
3. principal repayment reduces the borrower deposit and loan liability and
   the bank deposit liability and loan asset by the same amount.

## Canonical inputs and outputs

- `SFC_GOLD_1_CORPUS.json` is the canonical input, with stable event IDs,
  effective period, entity/sector registry, full instrument identity and
  decimal-string amounts.
- `audit_sfc_gold_oracle.py` independently checks event IDs, entity/sector
  membership, event-type posting composition, debit/credit equality,
  event-level holder/issuer mirrors, final instrument positions and sector
  financial net lending.
- Binary floating-point values are not permitted.
- The frozen output is:
  - household deposit asset: 7;
  - supplier deposit asset: 7;
  - bank deposit liabilities: 7 to household and 7 to supplier;
  - bank loan asset: 14;
  - household loan liability: 14;
  - system deposit assets = system deposit liabilities = 14;
  - sector financial net lending: CB 0, H -7, NFC +7; aggregate 0.

The oracle includes adversarial mutations for wrong holder identity, wrong
instrument identity, wrong entity/sector assignment, event-type relabelling,
and duplicate event delivery. These tests are designed so some mutations
preserve global debit/credit equality; the oracle must still reject them.

## Independence boundary

The oracle shares only the frozen JSON data contract with the system under
audit. It does not import or call `EntityJournal`,
`FinancialEventStore`, `append_validated_group`, or any production
projection. Its signed stock arithmetic and identity aggregation are
implemented independently. The frozen expected values are authored in the
corpus, not generated by the oracle at runtime.

## CI integration

The oracle is wired into:
- `prototype/test_a2_4_audit_controls.py`, so Prototype validation runs it;
- `.github/workflows/a2-4-audit-controls.yml`, so the dedicated A2.4 audit
  workflow executes it directly.

A successful local source write is not a test result. Exact-head CI, job
steps, logs, interpreter version and artifact evidence must be inspected
before any PASS claim.

## Explicit exclusions in v1

Interest accrual/settlement, FX revaluation, other-volume changes, impairment,
loss allowance, write-off, legal forgiveness, collateral, guarantees,
multi-period opening/closing continuity, trade credit, equity, government
securities, external assets, taxes, fees, capital and non-financial
counterpart transactions are not covered by this corpus.

These exclusions are intentional. They define the next extensions; they must
not be inferred from this initial PASS if and when CI succeeds.

## Cross-leg economic role invariants (v1 oracle hardening)

The oracle also checks the *relationships between legs*, not only each
instrument's local mirror. For the narrow no-FX v1 case it requires:

- origination to link the bank loan asset, borrower loan liability, borrower
  deposit asset and bank deposit liability to the same bank/borrower pair;
- supplier payment to link payer and supplier deposit-holder changes to the
  same issuing bank, with distinct holders and correct debit/credit direction;
- principal repayment to link the borrower, lending bank, loan mirror and
  deposit mirror consistently.

Loan accounts must carry the `loan` instrument class; deposit accounts must
carry `deposit`. Loan and deposit currencies must match for the v1 origination
and repayment fixtures. FX conversion is explicitly outside this version.

Adversarial controls additionally preserve local mirror equality while
mutating cross-leg borrower identity, and preserve a loan mirror while
misclassifying its instrument class. Both mutations must be rejected.

This is a source-level control contract, not a test result. Exact-head CI
execution remains required.


The v1 fixture is intentionally sector-specific: the bank role is CB, the
household borrower/payer role is H, and the supplier recipient role is NFC.
The oracle rejects a coordinated mutation that changes the bank's registry
sector and all corresponding posting labels while preserving internal
registry consistency. Loan and deposit instrument IDs must be distinct, as
must payer and supplier deposit instrument IDs. This is a frozen control
contract, not a general institutional-sector classification engine.


## Sequential stock and replay contract (v1)

The corpus declares exactly one positive effective period. Every event must
belong to that period. The JSON event array is the canonical replay order for
this single-period fixture; reordering it is a semantic mutation, not a
permitted alternative serialization.

The oracle maintains running positions and checks them after every complete
event. SFC-GOLD-1 v1 starts without opening positions and models no overdraft
facility, so every intermediate instrument position must remain non-negative.
This is a fixture-specific assumption, not a general rule for bank deposits,
credit facilities or ledgers with opening balances.

An instrument ID is immutable across the corpus: instrument class, currency,
maturity, denomination, valuation basis, holder and issuer cannot silently
change between events. A changed contract or holder requires a distinct
instrument identity or an explicit future lifecycle event contract.

Adversarial controls cover over-repayment despite balanced journal legs,
out-of-order repayment, changed maturity under a reused instrument ID, and
events assigned to an undeclared period. These controls are source implemented;
their execution remains subject to exact-head CI.


## Replay checkpoint extension — corpus v1.1.0

Version 1.1.0 preserves the v1 event economics and adds frozen expected
instrument positions after each canonical event. The oracle records the
running state after G1-E1, G1-E2 and G1-E3 and compares each checkpoint with
the corpus-authored expectation, rather than checking only the final state.

This closes a specific blind spot: a sequence could theoretically reach the
right closing balances while passing through an incorrect intermediate
allocation that later postings reverse. The checkpoint comparison now
constrains the complete path at each event boundary.

The checkpoints are data in the frozen corpus; the oracle does not generate
the expected values from its own result. The final checkpoint is consistent
with the six final holder/instrument positions already frozen in v1.0.0.

The extension does not add new economic event types, opening stocks,
multi-period accounting, interest, FX, impairment, write-off or legal
forgiveness. It remains a synthetic single-period reference case. Exact-head
CI execution is still required; no PASS is claimed.


The v1.1.0 oracle also contains a control that deliberately corrupts one
corpus-authored intermediate checkpoint while leaving the event stream
unchanged. The independent expected-output comparison must reject this
tampering. This is distinct from the twelve event-input mutations: it tests
that the reference expectations themselves are actually enforced.


## Corpus v1.2.0 — frozen holder/issuer identity and expectation integrity

Version 1.2.0 adds explicit `holder_entity_id` and
`issuer_entity_id` to every frozen final-position and per-event checkpoint
row. The oracle now compares those fields with the independently accumulated
instrument identity catalog. A liability-side row cannot silently change its
beneficial holder while preserving the same entity/account/instrument/balance
tuple.

The expected-position parser also rejects duplicate position keys rather than
silently collapsing them during dictionary construction, and requires
positive finite decimal-string balances. The v1.2.0 negative controls include:
- a corrupted intermediate checkpoint balance;
- a tampered expected deposit holder;
- a duplicate frozen final-position key;
- a duplicate frozen checkpoint-position key.

These are four frozen-expectation integrity controls in addition to the
twelve event-input mutations. This is still source-level control design;
execution and exact-head CI evidence remain pending.
