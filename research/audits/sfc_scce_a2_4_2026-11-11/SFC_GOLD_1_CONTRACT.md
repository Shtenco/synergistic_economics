# SFC-GOLD-1 — frozen financial-event corpus and independent oracle

## Status

**Source implementation committed; exact-head CI execution pending.** This is a
small synthetic control corpus, not empirical evidence, an accounting-standard
certification, or production-runtime integration.

## Purpose

SFC-GOLD-1 establishes a versioned, immutable reference case against which
financial-event semantics and downstream arithmetic can be independently
checked. The corpus is data-only JSON. The oracle is a separate executable
implementation and imports no production journal, SQLite event store,
adapter, SFC projection, or other audit fixture.

The first version deliberately freezes a narrow lifecycle rather than
pretending to cover every financial instrument:

1. bank loan origination creates a loan asset/liability and a matching deposit
   asset/liability;
2. supplier payment transfers an existing deposit from household to supplier
   without creating additional system deposits;
3. principal repayment reduces the borrower deposit and loan liability and
   the bank deposit liability and loan asset by the same amount.

## Canonical inputs and outputs

- `SFC_GOLD_1_CORPUS.json` is the canonical input, with stable event IDs,
  effective period, entity/sector registry, full instrument identity and
  decimal-string amounts.
- `audit_sfc_gold_oracle.py` independently checks event IDs, entity/sector
  membership, event-type posting composition, debit/credit equality,
  event-level holder/issuer mirrors, final instrument positions and sector
  financial net lending.
- Binary floating-point values are not permitted.
- The frozen output is:
  - household deposit asset: 7;
  - supplier deposit asset: 7;
  - bank deposit liabilities: 7 to household and 7 to supplier;
  - bank loan asset: 14;
  - household loan liability: 14;
  - system deposit assets = system deposit liabilities = 14;
  - sector financial net lending: CB 0, H -7, NFC +7; aggregate 0.

The oracle includes adversarial mutations for wrong holder identity, wrong
instrument identity, wrong entity/sector assignment, event-type relabelling,
and duplicate event delivery. These tests are designed so some mutations
preserve global debit/credit equality; the oracle must still reject them.

## Independence boundary

The oracle shares only the frozen JSON data contract with the system under
audit. It does not import or call `EntityJournal`,
`FinancialEventStore`, `append_validated_group`, or any production
projection. Its signed stock arithmetic and identity aggregation are
implemented independently. The frozen expected values are authored in the
corpus, not generated by the oracle at runtime.

## CI integration

The oracle is wired into:
- `prototype/test_a2_4_audit_controls.py`, so Prototype validation runs it;
- `.github/workflows/a2-4-audit-controls.yml`, so the dedicated A2.4 audit
  workflow executes it directly.

A successful local source write is not a test result. Exact-head CI, job
steps, logs, interpreter version and artifact evidence must be inspected
before any PASS claim.

## Explicit exclusions in v1

Interest accrual/settlement, FX revaluation, other-volume changes, impairment,
loss allowance, write-off, legal forgiveness, collateral, guarantees,
multi-period opening/closing continuity, trade credit, equity, government
securities, external assets, taxes, fees, capital and non-financial
counterpart transactions are not covered by this corpus.

These exclusions are intentional. They define the next extensions; they must
not be inferred from this initial PASS if and when CI succeeds.
